# Lab2. Service Profit Simulator

## Что здесь происходит

Лабораторная работа номер 2. В этом репозитории - эмулятор сервиса информационного брокера. Есть три типа запросов: краткая справка, досье, и кастомный анализ. Запросы проходят через кэш, серверы и очереди, могут задерживаться или завершаться ошибками.

Ваша задача - реализовать стратегию, которая управляет маршрутизацией, кэшем, заданиями и количеством серверов. За результат, которого клиент дождался, сервис получает деньги. За выделенные API-серверы и воркеры нужно платить. Цель - получить как можно больший Profit. Экспериментируйте с экономикой, разные запросы стоят по-разному.


### Как устроена система

Запросы принимает шлюз. Он обращается к вашей стратегии, чтобы решить, откуда получить ответ и кому назначить работу. Есть кэш, API-серверы, общая очередь фоновых заданий, воркеры и база данных.

API и воркеры - отдельные экземпляры. API обрабатывает несколько запросов одновременно, остальные ждут в его очереди. Воркерам задания назначает стратегия из общей очереди. База одна для всей системы, её мощность не увеличивается при добавлении серверов. Самими очередями управляет эмулятор.
Типы запросов:  

**Metadata - справка.** Небольшое чтение. Сначала проверяется кэш: можно выдать запись, присоединиться к уже идущей загрузке того же ключа или начать новую. На промахе Metadata обращается прямо к базе, без API. Если одновременно пришло несколько одинаковых запросов их можно объединить и сходить в базу только один раз - каждый клиент оплатит результат.

**Preview - досье.** Более тяжёлое чтение. Кэш работает так же, но новая загрузка проходит через API сервер, там обрабатывается, и затем идет в базу. Нужно выбрать API; запрос может ждать в его очереди.

**Generate - анализ.** Новый результат, который нужно вычислить. Запрос проходит через API, регистрируется как задание в общей очереди, затем назначается воркеру. Воркер выполняет работу и публикует результат в базе, после чего эмулятор уведомляет клиента. Кэш здесь не используется. Повтор регистрации не создаёт второе задание. За регистрацию денег нет - нужен готовый результат.

Цена запроса передаётся в `RequestInfo.Revenue`. Она может различаться даже у запросов одного типа, в том числе Generate. Это сумма за оплаченный результат, а не гарантия оплаты.

Система эмулирует неприятности реального мира. Серверы могут падать, сеть может терять запросы и ответы, вычисления и база - замедляться. Уже реализована система базового хэлсчека. Воркеры отправляют heartbeat - сообщения о том, что они работают. Потеря heartbeat не обязательно означает падение воркера.

Новые экземпляры запускаются не сразу. При остановке сервер сначала заканчивает принятую работу, но по истечении разрешённого времени останавливается принудительно. Оплачивается всё время от выделения до остановки, включая запуск, простой и сбои. В начале уже готовы два API и два воркера.

У каждого клиента есть скрытое терпение. Если он не дождался результата - оплаты не будет, но ваша стратегия об уходе не узнает. Общие примерные диапазоны терпения известны: Metadata - 0,5–1,5 секунды, Preview - 1–3 секунды, Generate - 15–60 секунд. В открытом сценарии у Generate более узкий диапазон: 15–35 секунд. Терпение выбирается случайно и не зависит от объёма работы. Точный срок отдельного клиента угадывать не нужно.

Для Metadata и Preview также важна свежесть. `MaxDataAge` задаёт допустимый возраст данных при доставке, а `SourceObservedAt` - когда данные фактически прочитали в источнике. Один ключ может запрашиваться с разными требованиями свежести: учитывайте требование каждого клиента, в том числе при общей загрузке. TTL определяет время хранения в кэше, но не делает запись новее. Слишком старый ответ денег не приносит.

Популярные ключи, их количество и доля обращений к ним могут меняться в ходе прогона.

### Реализация SystemPolicy

Вы должны создать класс, который реализует `ISystemPolicy`. Один и тот же экземпляр используется для всех запросов прогона, поэтому можно хранить состояние между вызовами и принимать решения на основании предыдущих результатов.

Когда метод получает `RequestInfo`, доступны ID и тип запроса, время поступления, цена, ключ данных, требование свежести и оценка работы. Точного времени будущего выполнения, терпения клиента и расписания отказов нет. В контекстах экземпляров есть их состояние, скорость, слоты, известные назначения и полученные heartbeat. Фактическая серверная работа после тайм-аутов может продолжаться, хотя шлюз её уже не ждёт.

**`OnCacheRead`** вызывается при поступлении Metadata или Preview. Получает запрос, текущее время, запись кэша или `null` и список идущих загрузок этого ключа. Верните `ServeCached()`, `JoinFetch(fetchId)` или `StartFetch()` из `CacheReadDecision`: выдать запись, присоединиться к загрузке или начать новую. Свежесть результата движок проверит при доставке каждому клиенту.

**`OnCacheFill`** вызывается после успешного получения данных из базы. Получает новое значение, текущие записи, лимит памяти и время. Верните `CacheWriteDecision.Skip()` либо `Retain(ttl, keysToEvict)`: не сохранять или сохранить с выбранным TTL, удалив указанные записи. Оставшееся содержимое должно помещаться в память. Отказ от сохранения не мешает дальше выдать полученный ответ клиентам - это только решение сохранять ли этот результат в кэше.

**`SelectEndpoint`** вызывается перед API-попыткой для Preview или регистрации Generate, включая повторы. Получает запрос, номер попытки, время и список подходящих API. Верните `EndpointSelectionDecision.Assign(apiId)`, `Reject()` или `null`: назначить API, окончательно отказать запросу или оставить его ждать. Ожидающий запрос движок предложит снова на очередном ревью. Для Metadata этот метод не вызывается.

**`ReviewEndpoint`** вызывается каждые 250 мс для API и воркеров в состоянии `Ready` или `Draining`, а для готового API ещё и после результата его вызова. Получает сведения об экземпляре, последние результаты его вызовов и проб, текущее время. Верните `EndpointDecision.Allow()`, `Block()` или `Probe()`: разрешить трафик, закрыть его или проверить экземпляр пробным запросом. Одновременно допускается одна проба на экземпляр. Блокировка не выключает сервер и не отменяет уже принятую работу.

**`SelectJobAssignment`** вызывается, когда есть готовое к назначению задание и свободный логический слот воркера. Получает время, списки заданий и доступных воркеров. Верните `JobAssignmentDecision.Assign(jobId, workerId)`, `Reject(jobId)` или `null`: выбрать пару, отказаться от задания или пока ничего не назначать. При ожидании очередь сохраняется, следующую возможность назначения обеспечит движок.

**`ReviewJob`** вызывается каждые 250 мс для назначенных, ещё не завершённых заданий. Получает задание, время его назначения, последний полученный heartbeat и текущее время. Верните `JobRecoveryDecision.KeepWaiting()` или `RequeueAfter(delay)`: ждать дальше или вернуть задание в очередь для повторного назначения после задержки. Старое выполнение может продолжаться, поэтому слишком раннее восстановление создаёт лишнюю работу. Опубликовать результат сможет только текущее поколение попытки.

**`ReviewCapacity`** вызывается при старте и затем каждую секунду. Получает время, выделенные экземпляры, ожидающие API-вызовы, задания и начисленные расходы. Цены, время запуска и ограничения ресурсов находятся в `context.Settings`. Верните `CapacityPlan` с желаемым общим количеством API и воркеров; можно также указать `RetireInstanceIds` - какие экземпляры выводить. Это целевое количество, а не число дополнительных запусков. Нельзя превышать лимиты каждой роли и общий бюджет вычислительных единиц.

**`Observe`** получает события: старт системы, поступление и завершение запросов, исходы RPC, heartbeat, назначение заданий, изменения кэша и экземпляров. В наблюдении есть вид события, время и относящиеся к нему поля. Возвращать ничего не нужно - обновляйте состояние стратегии. У технического `RequestFailed` передаются `Elapsed` от поступления запроса и явная `FailureReason`. Технический `RequestSucceeded` не означает, что клиент дождался ответа и заплатил.

**`GetProcessingBudget`** - необязательный метод. Вызывается один раз при поступлении запроса и получает `RequestInfo`. Можно вернуть положительную длительность обработки от момента поступления либо `null`, то есть не задавать лимит. По умолчанию метод возвращает `null`, его можно не реализовывать. При исчерпании бюджета приходит `RequestFailed` с причиной `ProcessingBudgetExceeded`. Нужно чтобы можно было ограничить суммарное время жизни запроса в системе.

Интервалы обзоров задаёт сценарий, стратегия их не меняет. Время везде модельное: используйте `Now` из контекстов и наблюдений, а не часы компьютера. Свои таймеры и ожидания создавать не нужно. В методы принятия решений передаётся `Random`; если нужны случайные числа, используйте его, как в первой лабораторной.

### RPC-стратегия из первой лабораторной

Свойство `RpcPolicy` возвращает объект `IRequestPolicy`. Можно использовать свою работу из первой лабораторной, разместив её внутри класса общей стратегии. Да конечно, лучше оставить реквест полиси отдельным файлом, но для простоты оценивания положите ее в файл SystemPolicy, чтобы в итоге все было в одном файле. 


### Структура солюшена

Два основных проекта:

`SPS.Student` - тут реализуете решение. `SampleSystemPolicy` - пример, чтобы посмотреть, как работают методы. Свою стратегию для сдачи разместите в ОДНОМ ФАЙЛЕ С УНИКАЛЬНЫМ НАЗВАНИЕМ, в котором должен быть класс, который реализует `ISystemPolicy` (туда же поместите вашу реквест полиси из первой лабы).  
`SPS.Runner` - запуск эмуляции. В `Program.cs` фабрика `CreateStudentPolicy` выбирает класс стратегии. После запуска программа покажет результат и, если задан trace, историю запросов.

Дополнительные проекты:

`SPS.Abstractions` - интерфейсы, контексты и классы решений.  
`SPS.Simulation` - движок эмуляции, менять его для выполнения работы не нужно.  
`SPS.Simulation.Public` - открытый сценарий для разработки.  
`SPS.Telemetry` - события и запись трассы.



В отчёте от Раннера есть Profit, выручка, расходы и результаты по типам запросов. Остальные метрики помогают понять, куда уходят ресурсы: задержки, повторы, кэш, восстановление и время жизни экземпляров. Средняя задержка и p95 считаются по успешным оплаченным запросам с учётом очередей и повторов.

### Оценивание

Сдаёте файл со своим классом, реализующим `ISystemPolicy`. Все вспомогательные классы, включая RPC-полиси, разместите внутри него. Решение должно зависеть только от `SPS.Abstractions`.

Ваша стратегия сравнивается с базовой на закрытом сценарии и 20 последовательных seed. На каждом seed обе получают одинаковые входные условия и новое состояние. Основной результат - Profit и его разница с базовой стратегией. Средний профит будет оценкой, по которой составим рейтинг решений. 

Открытый сценарий - пример для разработки. При проверке будут другие нагрузки, популярность данных, цены и отказы. Не подбирайте решение только под числа одного открытого запуска. Опирайтесь на наблюдения за системой и будьте готовы объяснить свои решения.
